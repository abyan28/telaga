# T9.1 — Akun Wali Murid Lama (Diskusi Plan)

> Mode plan. Belum ada kode. Tujuan: sepakati alur sebelum eksekusi.

## Masalah (dari notes.md T9.1)
Wali murid lama belum punya akun (PPDB dulu manual). Data siswa lama diinput admin/guru.
`students.id_guardian` NULLABLE — siswa lama saat ini biasanya **tanpa** baris `guardians`.
Butuh: cara wali lama punya akun untuk lihat tagihan/status anaknya, lalu ubah password sendiri.

## Fakta kode (sudah dicek)
- `users`: login by email/no_hp/username, `role` (wali/admin/guru), `password`.
- `guardians`: profil wali (nama, no_hp, pekerjaan), `id_user` → users. 1 user : 1 guardian.
- `students.id_guardian` → guardians (nullable). 1 guardian : banyak anak.
- Signup wali mandiri (`RegisterController`) sudah ada: buat user(role wali)+guardian, auto-login.
- Admin sudah CRUD akun admin (`AccountController`), CRUD siswa & guru (MasterData).
- **Belum ada**: kolom penanda "sudah punya akun / kode klaim" di students/guardians.

---

## Tiga opsi alur

### Opsi A — Admin buat akun + kartu kredensial (paling sederhana) ⭐ default
Admin, dari Profil Siswa (atau tab Data Siswa), klik "Buatkan Akun Wali".
- Sistem buat `users(role=wali)` + `guardians`, tautkan anak (`student.id_guardian`).
- Username = no_hp wali (diisi admin) ATAU email. Password awal = no_hp / NISN anak / string acak yang ditampilkan sekali.
- Admin serahkan kredensial ke wali (lisan/cetak). Wali login → ganti password (fitur ganti password wali sudah ada via T2.3? cek).
- Multi-anak: kalau wali sudah punya guardian, anak berikutnya tinggal di-assign ke guardian yg sama (jangan bikin akun dobel).

Pro: nol UI publik baru, reuse pola AccountController+guardian. Aman (tak ada self-claim yang bisa disalahgunakan).
Kontra: admin harus menyampaikan kredensial manual.

### Opsi B — Kode klaim (self-service wali)
Admin generate "kode klaim" per siswa/guardian. Wali buka halaman publik `/klaim`, masukkan kode + no_hp, set password sendiri.
- Butuh: kolom `guardians.claim_token` (+ expiry), halaman publik klaim, alur set-password.
Pro: wali mandiri, admin cuma bagi kode.
Kontra: +1 tabel-kolom, +halaman publik, +alur token = permukaan serang & kode lebih banyak. YAGNI untuk sekolah kecil (RA).

### Opsi C — Wali daftar sendiri lalu "klaim anak" by NISN
Wali signup biasa, lalu di dashboard masukkan NISN+tanggal lahir anak untuk mengklaim.
- Butuh: verifikasi pencocokan (NISN+tgl lahir), alur klaim di dashboard wali, guard anti-salah-klaim.
Pro: tak ada kerja admin.
Kontra: risiko klaim salah/menyerobot anak orang; butuh verifikasi identitas lebih ketat. Paling rawan.

## KEPUTUSAN FINAL (terkunci — siap eksekusi)

Opsi A. Semua wali lama:
- Tombol "Buatkan Akun Wali" di **tiap baris tabel Data Siswa** (admin/data/students.blade.php), muncul
  hanya bila siswa belum punya wali berakun (`student.guardian?->user` kosong). Input massal cepat.
- Klik → modal kecil isi **No HP wali** (+ nama wali, wajib untuk guardian baru).
- Backend `firstOrCreate` guardian by no_hp:
  - no_hp belum ada → buat `users(role=wali, username=no_hp, password=no_hp)` + `guardians(nama,no_hp)`.
  - no_hp sudah ada → pakai guardian itu (kakak-adik otomatis satu akun).
- Tautkan `student.id_guardian` ke guardian tsb. Audit log.
- **must_change_password**: flag baru `users.must_change_password` (bool, default false; true saat akun dibuat
  admin). Middleware paksa ganti-password. Berlaku 2 role:

  - **guru** (akun dibuat admin, password awal = NUPTK) → flag true. Guru sudah punya form ganti-password.
  - Wali BELUM punya form ganti-password (dicek: Wali/*password* = 0) → HARUS dibuat (bagian scope ini).
